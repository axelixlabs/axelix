## One version for every component

Axelix is released as a single, coordinated distribution. All components share **exactly the same version**.

When a new distribution of Axelix is released (say **Axelix OSS 3.1.2**), every released component carries that
same version `3.1.2`:

- The **Spring Boot Starters** (published as Maven artifacts).
- The **plugins** (also published as Maven artifacts).
- The **Axelix Master** standalone JAR.
- The **Axelix Master** Docker image.
- The **Axelix Master** Helm chart.

There is no independent versioning per component. If you know the version of one Axelix artifact, you know the version
of them all in that release.

This holds for **patch releases too**: a patch re-releases the whole fleet under `X.Y.Z`, cut from the minor line's
patch branch. See [Branching Model](./development/branching-model.mdx) and [Releases](./development/releases.mdx)
for how those cuts happen.

### Artifact names

Every release is tagged `v<version>` in the repository, for example `v1.3.0`. Master ships as a JAR, a Docker image,
and a Helm chart, and all three are named `axelix` followed by the release version. So once you know the version, you
know the name of every file and tag. For Axelix `1.3.0` the artifacts are:

| Artifact             | Name                                                                   | Where to get it                                                                                                                                                   |

| Master JAR           | `axelix-1.3.0.jar`                                                     | **Assets** of the [`v1.3.0` release](https://github.com/axelixlabs/axelix/releases/tag/v1.3.0)                                                                    |
| Master Docker image  | `axelix:1.3.0`                                                         | `ghcr.io/axelixlabs/axelix` and `docker.io/axelixlabs/axelix`                                                                                                     |

## What the version number means

An Axelix version has three parts, `MAJOR.MINOR.PATCH`, for example `1.4.2`. It looks like
[Semantic Versioning](https://semver.org/), but Axelix doesn't follow it strictly. Under semver, only a major release
may break anything, while a minor release just adds features. Axelix follows the
[versioning approach of Spring Boot](https://github.com/spring-projects/spring-boot/wiki/Team-Practices#versioning)
instead, where a minor release may contain breaking changes too. Spring Boot's
[Supported Versions](https://github.com/spring-projects/spring-boot/wiki/Supported-Versions) policy says so directly:
"Minor and major releases might contain back-incompatible API changes."

### Why not strict semantic versioning

The reason is the size of the public API. Axelix, like Spring Boot, is a large project. Its starters run inside your
application, Master has many configuration properties, and the components talk to each other over their own protocols.
With a surface that large, almost every change touches something a user could depend on. Under strict semver, nearly
every release would then have to be a major one, so the major version would stop telling you anything useful.

The Spring Boot team describes exactly this problem in its
[team practices](https://github.com/spring-projects/spring-boot/wiki/Team-Practices#versioning): "It's not really
possible for Spring Boot to use semantic versioning since every release would have to be a major."

### The pain index

Instead of promising "no breaking changes at all", Axelix uses the version number as a **pain index**. The part of the
version that changes tells you how much work the upgrade is likely to cost you. This is the same idea Spring Boot
[describes](https://github.com/spring-projects/spring-boot/wiki/Team-Practices#versioning) for its own releases: "we try
to use the version number as an indicator of the amount of pain that an upgrade will cause."

| Upgrade | Example            | What to expect                                                                                                                                                                              |
|---------|--------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Patch   | `1.4.2` → `1.4.3`  | A drop-in replacement. It carries bug fixes, security fixes, or performance improvements, and you don't need to change anything.                                                           |
| Minor   | `1.4.x` → `1.5.0`  | New features, and possibly a few breaking changes. In most cases nothing on your side changes. When something does, the adjustment is small.                                                |
| Major   | `1.x.x` → `2.0.0`  | Many new features and almost certainly breaking changes that affect your setup. Plan time for the migration: each major version has a dedicated migration guide.                           |

Which parts of Axelix may change in a minor release, and which stay fixed until the next major, is spelled out below in
[Compatibility between components](#compatibility-between-components) and
[Backward compatibility guarantees between releases](#backward-compatibility-guarantees-between-releases). For the
upgrade procedure itself, see [Upgrading Axelix](./upgrading.mdx).

## A dedicated starter per Spring Boot major version

Axelix ships a **dedicated starter for every Spring Boot major version**. There is a standalone, separate artifact for
each supported major:

- `axelix-spring-boot-2-starter`: for Spring Boot **2.x** services.
- `axelix-spring-boot-3-starter`: for Spring Boot **3.x** services.
- `axelix-spring-boot-4-starter`: for Spring Boot **4.x** services.

As of now, Axelix supports Spring Boot **major versions 2 through 4**. Pick the starter that matches your service's
Spring Boot major version.

**Plugins** are different: they are designed to be broadly compatible, so there is no per-version plugin artifact to
choose from:

- The **Gradle plugin** is tested to work on Gradle major versions **5 through 9**.
- The **Maven plugin** is compatible with **Maven 3**, which is what virtually every Maven project uses today.

:::info[Minimum Spring Boot 2 version is 2.7.x]
`axelix-spring-boot-2-starter` supports Spring Boot 2 starting from **2.7**, not the whole 2.x line. If your service
is on an earlier Spring Boot 2.x (some services run as far back as **2.5.15**), you must upgrade to at least
**Spring Boot 2.7** before adding Axelix.
:::

## Java version compatibility

**Axelix Master** is itself a Spring Boot application, written on **Java 25**. This will be the concern only in case you'd
want to run Axelix Master as a JAR. In any other case it will not make a difference.

**Starters** follow the Java compatibility of the Spring Boot version they target. Each starter is compatible with **any
Java version that its Spring Boot major supports**. For example, Spring Boot 3 supports Java **17** at the very least and
up to Java **25** (with Spring Boot 3.5), depending on the minor version you run, and `axelix-spring-boot-3-starter`
follows exactly the same range.

:::info[Minimum Java version is 11]
The one exception to "follow Spring Boot's Java support" is a hard **floor of Java 11** for Axelix **starters and
plugins**. Spring Boot 2 users who can theoretically still be on **Java 8** cannot use Axelix: they must upgrade to at
least **Java 11**.
:::

## Compatibility between components

Axelix is [released in lockstep](#one-version-for-every-component), but you can **upgrade** components at different
times. Two compatibility rules apply:

- **Master and starter:** within one major version, Master supports starters from the last **4 minor releases, counting
  its own**. The starter must not have a newer minor version than Master. This window applies since Axelix 1.1; see
  [Upgrading Axelix](./upgrading.mdx).
- **Starter and build plugin:** within a service, both must share the same `major.minor` version.

**Patch versions are irrelevant to both rules.**

- ✅ Master `1.4.2`, starter `1.4.5`, plugin `1.4.0`: guaranteed compatible.
- ✅ Starter `1.4.3` with plugin `1.4.0`: same `1.4`, guaranteed compatible.
- ✅ Master `1.4.2` with starter `1.3.4`: inside Master's `1.1`–`1.4` window, guaranteed compatible.
- ⚠️ Master `1.4.x` with starter `1.0.x` or `1.5.x`: outside the supported window.
- ⚠️ Starter `3.1.x` with plugin `3.3.x`: different minor versions, not guaranteed and unsupported.
- ⚠️ Master and starter on different major versions: outside the compatibility window; follow the major migration guide.

Keeping everything on exactly the same `X.Y.Z` is the simplest policy. If you upgrade components separately, keep
each starter inside Master's supported window and aligned with its plugin.

### Why patch drift is safe but minor/major drift is not

For a starter and its build plugin, contracts may change between minor releases, so only matching `major.minor`
versions are supported. Master-to-starter communication has the wider four-minor compatibility window described above.

Patch releases may carry a **critical CVE fix, a bug fix, or a performance improvement**. A patch re-publishes the
**whole fleet**, although the actual fix usually touches only some components. Upgrading just an affected component
and leaving the others on an older patch stays compatible under the two rules above.

:::warning[Keep each pairing within its supported range]
Do not run a starter with a newer minor version than Master or more than three minor releases behind it, and do not mix major versions
between Master and starter. The Master-to-starter window does not apply to starter-to-plugin compatibility: keep
those two on the same `major.minor` version.
:::

## Backward compatibility guarantees between releases

### Axelix Master

Axelix Master is a Java application meant to be **run as a standalone process**: in Kubernetes, in Docker, or as a
plain JAR. It is **not** meant to be consumed as a library. Because of that, we **do not** treat the Java public
surface as a public contract: **public classes, public methods, constructors, fields, enums, and constants are all
considered internal**.

In practice this means we may change that public Java API in **minor or even patch** releases. The assumption is that
nobody depends on Master as a library, so mutating its Java API freely lets us **move development faster**. It is a
deliberate trade-off that realistically affects almost no one, and a big win for the pace of the project.

What we **do** treat as Master's public contract is its **configuration**:

- The **names** of properties, both for the Axelix Master **Helm chart** and for Axelix Master run as a **standalone
  JAR**.
- Their **default values**.
- Their **types**.

These will change **only in major releases**.

:::info[Rule of thumb for Master]
Depend on Master's **properties** (names, defaults, types): those are stable within a major version. Do **not** depend
on Master's Java classes, methods, or other code-level members: those can change in any release.
:::

### Starters

Starters **are** consumed as libraries. They are Spring Boot starters, so they bring auto-configurations with beans
into your application (bootstrap wiring, the internal proxying strategy, and so on). That reality shapes two rules.

**Do not override Axelix beans.** We intentionally **do not** allow end users to override the internal beans Axelix
declares in order to tinker with the bootstrap process, the proxying strategy, or similar internals. This is a
deliberate choice. Axelix works hard to add **no measurable overhead** to your app and to be as efficient and bug-free
as possible; letting you override beans like `BeanPostProcessor`s or `ProxyFactoryBean` instances would open a backdoor
to subtle bugs and worse performance. So please do not try to swap out Axelix's beans.

**Do not depend on a starter's public Java API.** We have to acknowledge that starters run inside real applications, so
their public Java API *can* technically be reached from your code, but this is **not intended**, and we strongly
discourage it. To move fast and stay competitive, we **may** change the public Java API of the starters too. We will
avoid it at all costs, but if we deem it necessary we may change it in a **minor** version bump.

:::tip[Missing a feature? File an issue instead of tinkering]
The rule of thumb is simple: if you need something, or a feature is missing, **do not tinker with the starter**. Open
an issue in our [GitHub issue tracker](https://github.com/axelixlabs/axelix/issues). We promise to review it. When we
add the feature you requested, we will give you a **property** to control that behavior: a stable, supported knob
rather than a bean override or a code-level dependency.
:::
