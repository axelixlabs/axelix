[Spring Boot Admin](https://github.com/codecentric/spring-boot-admin) (SBA) was an early inspiration for Axelix.
The engineers building Axelix have used SBA in real environments for years. A central UI for Spring Boot Actuator
is a useful starting point, but the problems teams need to solve extend well beyond displaying Actuator data.

That experience led to a broader scope: **Axelix is the open-source, AI-native platform for developing and evolving
Java Spring Boot microservice ecosystems.** It covers familiar application-management workflows with role-based
access control built in, adds deeper inspection and runtime control, and helps teams manage change across services.
Both human engineers and AI agents are intended users of the platform.

## Familiar management workflows, with RBAC built in

Axelix covers the everyday workflows teams turn to SBA for: inspecting application state, viewing metrics,
changing logger levels, examining configuration, and working with caches. These capabilities come with a built-in
identity and permission model.

Master provides local users, OAuth2/OIDC sign-in, role mapping, and operation-level authorities. For example,
permissions govern clearing caches, modifying scheduled tasks, and reading sensitive property values.
Master authenticates human and MCP clients, checks access, and uses signed JWTs when calling managed services.
See [Authentication](../setting-up-master-ui/authentication/authentication.mdx) for the permission model.

SBA provides integration points for Spring Security, but **your team must implement and maintain the IAM integration
and authorization rules for its deployment**. This means writing security configuration, connecting user identities
to roles, and wiring checks that decide who can read sensitive data or invoke management actions. You must also secure
the managed applications' Actuator endpoints. SBA's
[security documentation](https://docs.spring-boot-admin.com/4.1.4/docs/security/) shows the configuration and code involved.

Security integration is detailed work, and getting it right is not always easy. A missed authorization check or an
incorrect role mapping can expose sensitive information or allow unintended changes to running services. Your team
owns the implementation, testing, and ongoing maintenance of those checks.

**Axelix ships this security model as part of the product.** User management, identity-provider integration, role mapping,
and operation-level access checks are already wired into Master. You configure your identity provider and access policy
using the supplied mechanisms, rather than writing and maintaining the authorization integration yourself.

Axelix Master is also ready to deploy as a standalone JAR with the UI and MCP server bundled, an official Docker image,
or an official Helm chart. See [Configuring Master](../setting-up-master-ui/configuring-master/configuring-master.mdx).
You add the Axelix starter and build plugin to each managed application.

## Deeper inspection and control inside each application

SBA primarily presents the management capabilities exposed by standard Spring Boot and Spring Cloud Actuator endpoints.
Its [installation guide](https://docs.spring-boot-admin.com/3.5.1/docs/installation-and-setup/) describes this model.
**This significantly limits the depth of inspection and control available through SBA out of the box:** it can only
show the information and offer the actions those native endpoints expose.

During an incident, that information is often insufficient to explain what happened inside the application. A task listing, for example, does not explain
why a particular execution failed, and it does not allow to execute the given scheduled-task on demand.
Custom extensions can fill these gaps, but your team must write and maintain additional application and console code.

Axelix's [Spring Boot Starter](../setting-up-spring-boot-service/spring-boot-starter/what-is-spring-boot-starter.mdx)
collects additional runtime information and implements actions beyond those standard endpoints. Some collectors enrich
Actuator data; others instrument application behavior directly. This lets Axelix answer more detailed questions and
provide more control in the same debugging workflow.

:::note[Planned move away from custom Actuator endpoints]
Today, the starter exposes Axelix's own `axelix-*` Actuator endpoints. These carry capabilities beyond the standard
Actuator API. [Issue #1858](https://github.com/axelixlabs/axelix/issues/1858) tracks the planned migration to independent
Axelix APIs because of configuration interference, security concerns, constraints imposed by Actuator abstractions,
and portability. The replacement API design is still under discussion. This is a planned change, not the current transport.
:::

### Scheduled tasks and their executions

Listing a cron expression is only the start of understanding a scheduled job. Axelix records task executions,
including duration and failures, so you can investigate what happened when a job ran. You can also run a task on demand,
enable or disable it, and change its cron expression, fixed delay, or fixed rate without redeploying.
See [Scheduled Tasks](../features/spring-framework/scheduled-tasks.mdx).

### Temporary logging changes across replicas

When a problem can occur on any replica, changing one instance at a time makes investigation harder.
Axelix lets you change a logger's level across selected instances of the same application for a limited time.
When that time expires, the previous level is restored automatically. Logger groups can also be changed across
instances, while temporary levels apply to individual loggers.
See [Loggers](../features/insights/loggers/loggers.mdx).

### Effective property values and the beans that use them

A property in `application.yaml` does not necessarily determine the value the running application uses.
Axelix shows the winning property source and the values suppressed by higher-precedence sources.
It links properties to their `@Value` consumers and `@ConfigurationProperties` beans, and shows bound configuration values.

Because inspection should also help find mistakes, Axelix flags known dangerous effective values and properties marked
as deprecated in Spring Boot configuration metadata. Sensitive values remain subject to access permissions and masking.
See [Properties](../features/spring-framework/properties.mdx) and
[Configuration Properties](../features/spring-framework/configuration-properties.mdx).

### Beans and why they exist

Axelix adds context to the bean list: dependencies, origin, qualifiers, proxy type, and links to the relevant
auto-configuration. Together with the conditions report, this helps explain why Spring created a bean and how it fits
into the application. See [Beans](../features/spring-framework/beans.mdx) and
[Conditions](../features/spring-framework/conditions.mdx).

### Transaction executions and anti-patterns

Axelix monitors transaction executions and aggregates their average, fastest, and slowest durations.
It detects blocking `RestTemplate` calls inside transactions, N+1 lazy-loading queries, and Hibernate in-memory
pagination, with details that help locate the problem in code. These are application-level diagnostics beyond
standard Actuator inspection. See [Transaction Control](../features/spring-framework/transaction-control.mdx).

## From individual services to ecosystem evolution

Runtime debugging is one part of Axelix's scope. Teams also need to understand what their ecosystem depends on
and how it is evolving.

- **Java and Spring Boot migrations.** [Spring Portfolio](../ui-guide/dashboard/spring-portfolio.mdx) and
  [Languages Profile](../ui-guide/dashboard/languages-profile.mdx) show the Spring and Java versions in use across
  applications, so teams can track migration progress.
- **Dependency health.** The [Dependency Health dashboard](../ui-guide/dashboard/dependency-health.mdx)
  shows library usage, versions, and maintenance status across the ecosystem. Per-instance
  [dependency analysis](../features/insights/dependencies-analyzer.mdx) helps investigate an individual application's libraries.

These views connect a problem in one service to work across the entire ecosystem, such as replacing an unmaintained
library or moving applications to a supported Spring Boot generation.

## AI-native workflows

Axelix is designed for engineers and AI agents to work with application diagnostics directly.
Its bundled MCP server exposes runtime inspection, application metadata, persistence findings, and supported runtime
actions to agents, with access checks integrated into Master. An agent can find a service, inspect its beans and
configuration, investigate detected persistence problems, or change a logger level through tools.

The [MCP tool catalog](../setting-up-master-ui/mcp/mcp-tools.mdx) lists current coverage. It does not yet include every
UI operation. The platform's AI-native direction is to make its analysis and control capabilities usable by agents
as well as humans.

SBA also now documents an [experimental MCP integration](https://docs.spring-boot-admin.com/4.1.4/docs/mcp/).
The distinction is therefore the depth and scope of the information and actions exposed, alongside Axelix's integrated
permission model and broader ecosystem capabilities.

## Feature comparison

This compares the standard SBA workflows with capabilities shipped in Axelix OSS. SBA can be extended, and features
vary by version. Its newer MCP integration is called out explicitly rather than treated as absent.

| Area | Spring Boot Admin | Axelix |
|------|-------------------|--------|
| Application state, metrics, configuration, loggers | Standard Actuator-backed management | Included, with additional runtime information and controls |
| User management and operation-level RBAC | Implement and maintain IAM integration and authorization rules through Spring Security | Built-in local users, OIDC role mapping, and authorities |
| Authentication to managed services | Configure Actuator security and credentials | Integrated Master-to-starter JWT authentication |
| Temporary logger levels with automatic restoration across replicas | — | Included ([Loggers](../features/insights/loggers/loggers.mdx)) |
| Property inspection | Actuator environment and configuration properties | Effective and suppressed values, bean links, deprecation metadata, dangerous-value checks |
| Bean inspection | Actuator bean descriptors | Enriched origin, qualifiers, proxy information, and auto-configuration links |
| Scheduled tasks | Actuator task listing | Execution history, durations, failures, on-demand runs, enable/disable, rescheduling |
| Transaction diagnostics | — | Execution statistics and detected anti-patterns |
| Cache management | Standard Actuator inspection and clearing | Inspection, clearing, and runtime enable/disable ([Caches](../features/spring-framework/caches.mdx)) |
| Java / Spring Boot migration tracking | — | Ecosystem-wide Spring Portfolio and Languages Profile |
| Dependency maintenance health | — | Per-instance analysis and ecosystem dashboard |
| AI-agent access | Experimental MCP module in newer SBA versions | Bundled MCP server with application inspection, diagnostics, and supported actions |
| Ready-to-run distribution | Assemble and configure an SBA application | Standalone JAR, official Docker image, official Helm chart |
