## Eine Version für alle Komponenten

Axelix wird als eine koordinierte Distribution veröffentlicht. Alle Komponenten tragen **exakt dieselbe Version**.

Erscheint eine neue Distribution, etwa **Axelix OSS 3.1.2**, trägt jede veröffentlichte Komponente dieselbe Version `3.1.2`:

- Die **Spring Boot Starter**, veröffentlicht als Maven-Artefakte.
- Die **Plugins**, ebenfalls als Maven-Artefakte.
- Die eigenständige **Axelix-Master**-JAR.
- Das **Axelix-Master**-Docker-Image.
- Das **Axelix-Master**-Helm-Chart.

Es gibt keine unabhängige Versionierung pro Komponente. Kennen Sie die Version eines Axelix-Artefakts, kennen Sie auch die Version aller anderen dieser Veröffentlichung.

Das gilt **auch für Patch-Versionen**: Ein Patch veröffentlicht alle Komponenten erneut unter `X.Y.Z` aus dem Patch-Branch der Minor-Linie.
Das Verfahren beschreiben [Branching-Modell](./development/branching-model.mdx) und [Veröffentlichungen](./development/releases.mdx).

### Artefaktnamen

Jede Veröffentlichung erhält im Repository einen Tag `v<version>`, etwa `v1.3.0`.
Master erscheint als JAR, Docker-Image und Helm-Chart. Alle drei heißen `axelix`, gefolgt von der Versionsnummer.
Wenn Sie die Version kennen, kennen Sie daher alle Datei- und Tag-Namen. Für Axelix `1.3.0` sind dies:

## Bedeutung der Versionsnummer

Eine Axelix-Version besteht aus `MAJOR.MINOR.PATCH`, etwa `1.4.2`.
Das ähnelt [Semantic Versioning](https://semver.org/), Axelix folgt diesem Modell aber nicht strikt.
Nach Semver dürfen nur Major-Versionen inkompatible Änderungen enthalten, während Minor-Versionen nur Funktionen ergänzen.
Axelix folgt stattdessen dem [Versionierungsansatz von Spring Boot](https://github.com/spring-projects/spring-boot/wiki/Team-Practices#versioning),
nach dem auch Minor-Versionen inkompatible Änderungen enthalten dürfen.
Die Richtlinie [Supported Versions](https://github.com/spring-projects/spring-boot/wiki/Supported-Versions) formuliert dies ausdrücklich:
„Minor- und Major-Versionen können rückwärtsinkompatible API-Änderungen enthalten.“

### Warum kein striktes Semantic Versioning?

Der Grund ist der Umfang der öffentlichen API. Axelix ist wie Spring Boot ein großes Projekt.
Seine Starter laufen innerhalb Ihrer Anwendung, Master hat viele Konfigurationseigenschaften, und die Komponenten kommunizieren über eigene Protokolle.
Bei einer so großen Oberfläche betrifft fast jede Änderung etwas, auf das sich ein Benutzer verlassen könnte.
Unter striktem Semver müsste daher fast jede Veröffentlichung eine Major-Version sein. Die Major-Nummer verlöre ihren Informationswert.

Das Spring-Boot-Team beschreibt genau dieses Problem in seinen [Team-Praktiken](https://github.com/spring-projects/spring-boot/wiki/Team-Practices#versioning):
„Spring Boot kann Semantic Versioning praktisch nicht verwenden, da jede Veröffentlichung eine Major-Version sein müsste.“

### Der Aufwandsindikator

Statt keinerlei inkompatible Änderungen zu versprechen, verwendet Axelix die Versionsnummer als **Aufwandsindikator**.
Der geänderte Teil zeigt, wie viel Arbeit eine Aktualisierung voraussichtlich erfordert.
Spring Boot [beschreibt](https://github.com/spring-projects/spring-boot/wiki/Team-Practices#versioning) dieselbe Idee:
„Wir versuchen, die Versionsnummer als Indikator dafür zu verwenden, wie schmerzhaft eine Aktualisierung wird.“

| Aktualisierung | Beispiel          | Erwartung                                                                                                                                                                                                   |
| -------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Patch          | `1.4.2` → `1.4.3` | Direkt austauschbar. Enthält Fehler- und Sicherheitskorrekturen oder Leistungsverbesserungen. Sie müssen nichts ändern.                                                                                     |
| Minor          | `1.4.x` → `1.5.0` | Neue Funktionen und möglicherweise einige inkompatible Änderungen. Meist bleibt auf Ihrer Seite alles unverändert. Wenn Anpassungen nötig sind, sind sie klein.                                             |
| Major          | `1.x.x` → `2.0.0` | Viele neue Funktionen und mit hoher Wahrscheinlichkeit inkompatible Änderungen an Ihrer Einrichtung. Planen Sie Zeit für die Migration ein. Für jede Major-Version gibt es eine eigene Migrationsanleitung. |

Welche Teile sich in einer Minor-Version ändern dürfen und welche bis zur nächsten Major-Version stabil bleiben, erläutern
[Kompatibilität zwischen Komponenten](#kompatibilität-zwischen-komponenten) und
[Garantien zur Rückwärtskompatibilität zwischen Veröffentlichungen](#garantien-zur-rückwärtskompatibilität-zwischen-veröffentlichungen).
Das Aktualisierungsverfahren selbst beschreibt [Axelix aktualisieren](./upgrading.mdx).

## Ein eigener Starter pro Spring-Boot-Major-Version

Axelix liefert einen **eigenen Starter für jede Spring-Boot-Major-Version**. Für jede unterstützte Major-Version gibt es ein separates Artefakt:

- `axelix-spring-boot-2-starter`: für Dienste mit Spring Boot **2.x**.
- `axelix-spring-boot-3-starter`: für Dienste mit Spring Boot **3.x**.
- `axelix-spring-boot-4-starter`: für Dienste mit Spring Boot **4.x**.

Derzeit unterstützt Axelix die Spring-Boot-**Major-Versionen 2 bis 4**. Wählen Sie den Starter passend zur Major-Version Ihres Dienstes.

**Plugins** sind anders: Sie sollen breit kompatibel sein. Deshalb gibt es keine getrennten Plugin-Artefakte pro Version:

- Das **Gradle-Plugin** wird mit den Gradle-Major-Versionen **5 bis 9** getestet.
- Das **Maven-Plugin** ist mit **Maven 3** kompatibel, das heute nahezu alle Maven-Projekte verwenden.

:::info[Spring Boot 2 wird ab 2.7.x unterstützt]
`axelix-spring-boot-2-starter` unterstützt Spring Boot 2 ab **2.7**, nicht die gesamte 2.x-Linie.
Verwendet Ihr Dienst eine ältere Spring-Boot-2.x-Version, etwa **2.5.15**, müssen Sie vor dem Hinzufügen von Axelix auf mindestens **Spring Boot 2.7** aktualisieren.
:::

## Java-Versionskompatibilität

**Axelix Master** ist selbst eine Spring-Boot-Anwendung auf **Java 25**.
Das ist nur relevant, wenn Sie Master als JAR ausführen möchten. Bei anderen Bereitstellungsformen macht es keinen Unterschied.

**Starter** folgen der Java-Kompatibilität der jeweiligen Spring-Boot-Version.
Jeder Starter ist mit **jeder von seiner Spring-Boot-Major-Version unterstützten Java-Version** kompatibel.
Spring Boot 3 unterstützt beispielsweise mindestens Java **17** und je nach Minor-Version bis Java **25** mit Spring Boot 3.5.
`axelix-spring-boot-3-starter` folgt genau diesem Bereich.

:::info[Mindestens Java 11]
Die einzige Ausnahme von der Spring-Boot-Java-Kompatibilität ist die feste **Untergrenze Java 11** für Axelix-**Starter und Plugins**.
Spring-Boot-2-Benutzer, die theoretisch noch **Java 8** verwenden können, müssen für Axelix auf mindestens **Java 11** aktualisieren.
:::

## Kompatibilität zwischen Komponenten

Axelix wird [gemeinsam veröffentlicht](#eine-version-für-alle-komponenten), muss aber nicht gemeinsam **aktualisiert** werden.
In einer realen Dienstlandschaft kann Master bereits den neuesten Patch haben, während Dienste noch nachziehen.
Oder Sie aktualisieren den Starter eines einzelnen Dienstes, während alles andere unverändert bleibt.
Für solche gemischten Bereitstellungen gilt eine Regel für **jede** Axelix-Komponente:

> **Zwei beliebige Axelix-Komponenten sind garantiert kompatibel, solange sie dieselbe `major`- und `minor`-Version haben. Die Patch-Version spielt keine Rolle.**

Dies ist der vollständige Vertrag. Er gilt für alle Kombinationen: Master mit Starter, Starter mit Plugin und alle gemeinsam.
Eine Kompatibilitätsmatrix ist nicht nötig. Stimmen Sie einfach `major.minor` ab.

- ✅ Master `1.4.2`, Starter `1.4.5`, Plugin `1.4.0`: alle auf `1.4`, garantiert kompatibel.
- ✅ Starter `1.4.3` mit Plugin `1.4.0`: dieselbe `1.4`, garantiert kompatibel.
- ⚠️ Master `1.4.2` mit Starter `1.3.4`: **abweichende Minor-Versionen**, nicht garantiert. Kann funktionieren oder fehlschlagen.
- ⚠️ Starter `3.1.x` mit Plugin `3.3.x`: **abweichende Minor-Versionen**, nicht garantiert und nicht unterstützt.
- ⚠️ Jede **Major-Abweichung**: nicht garantiert und noch weniger wahrscheinlich funktionsfähig als eine Minor-Abweichung.

Bei unterschiedlichen **Minor- oder Major-Versionen** garantieren wir **nichts**.
Die Kombination kann funktionieren, aber auch fehlschlagen, und sie wird nicht getestet.
Die einfachste Richtlinie ist, alles auf exakt demselben `X.Y.Z` zu halten, was gemeinsame Veröffentlichungen leicht machen.
Der eigentliche Vertrag gilt jedoch nur für `major.minor`.

### Warum unterschiedliche Patch-Stände sicher sind, Minor- und Major-Abweichungen jedoch nicht

Diese Richtlinie setzt voraus, dass **sämtliche Komponentenfunktionen über die Axelix-Master-Weboberfläche genutzt werden sollen**.
Es gibt keinen vorgesehenen Fall, in dem nur die **Minor-Version** einer einzelnen Komponente erhöht wird, um eine Funktion freizuschalten:
Die Funktion ist über Master verfügbar, nicht über die isolierte Komponente.
Deshalb erlauben wir uns, **Verträge zwischen Komponenten in Minor-Versionen zu überarbeiten**, um die Entwicklung schnell voranzubringen.

Patch-Veröffentlichungen unterscheiden sich davon. Wie [Semver](https://semver.org/) beschreibt, können sie eine **kritische CVE-Korrektur,
eine Fehlerbehebung oder eine Leistungsverbesserung** enthalten, die **für sich genommen** wertvoll sind.
Ein Patch veröffentlicht **alle Komponenten** unter der neuen Version erneut, aber die tatsächliche Korrektur betrifft meist nur einige davon.
Daher ist es realistisch, nur die betroffene Komponente zu aktualisieren und andere auf einem älteren Patch zu lassen. Wir garantieren die Kompatibilität dieser Kombination.

:::warning[Minor- und Major-Abweichungen können Kommunikationsprotokolle brechen]
Wir **können** die Protokolle zwischen Komponenten (Master ↔ Starter, Plugin ↔ Starter) zwischen **Minor-Versionen** überarbeiten,
erst recht zwischen **Major-Versionen**. Das bedeutet ausdrücklich nicht, dass wir es tun werden, aber wir können es.
Jede Kombination über eine Minor-Grenze hinweg **kann** daher fehlschlagen. Ein Fehler ist nicht zwangsläufig, aber wir garantieren nichts anderes.
Halten Sie alle Komponenten auf derselben Major- **und** Minor-Version. Nur die Patch-Stände dürfen abweichen.
:::

## Garantien zur Rückwärtskompatibilität zwischen Veröffentlichungen

### Axelix Master

Axelix Master ist eine Java-Anwendung zum **Betrieb als eigenständiger Prozess**, in Kubernetes, Docker oder als einfache JAR.
Er ist **nicht** als Bibliothek gedacht. Deshalb betrachten wir die öffentliche Java-Oberfläche **nicht** als öffentlichen Vertrag:
**Öffentliche Klassen, Methoden, Konstruktoren, Felder, Enums und Konstanten gelten als intern.**

In der Praxis können wir diese Java-API in **Minor- oder sogar Patch-Versionen** ändern.
Wir gehen davon aus, dass niemand Master als Bibliothek verwendet. Freie API-Änderungen ermöglichen daher **schnellere Entwicklung**.
Dieser bewusste Kompromiss betrifft realistisch fast niemanden und beschleunigt das Projekt erheblich.

Masters **Konfiguration** betrachten wir hingegen als öffentlichen Vertrag:

- Die **Namen** von Eigenschaften, sowohl im **Helm-Chart** als auch bei der Ausführung als **eigenständige JAR**.
- Ihre **Standardwerte**.
- Ihre **Typen**.

Diese ändern sich **nur in Major-Versionen**.

:::info[Faustregel für Master]
Verlassen Sie sich auf Masters **Eigenschaften** mit Namen, Standardwerten und Typen. Sie bleiben innerhalb einer Major-Version stabil.
Verlassen Sie sich **nicht** auf Java-Klassen, Methoden oder andere Codeelemente von Master. Diese können sich in jeder Version ändern.
:::

### Starter

Starter werden **als Bibliotheken** verwendet. Als Spring-Boot-Starter bringen sie Autokonfigurationen mit Beans in Ihre Anwendung,
etwa für die Startverdrahtung und die interne Proxy-Strategie. Daraus folgen zwei Regeln.

**Überschreiben Sie keine Axelix-Beans.** Endbenutzer dürfen die internen Axelix-Beans bewusst **nicht** überschreiben,
um Startprozess, Proxy-Strategie oder ähnliche Interna zu verändern.
Axelix soll **keinen messbaren Mehraufwand** verursachen und möglichst effizient und fehlerfrei sein.
Das Überschreiben von Beans wie `BeanPostProcessor`s oder `ProxyFactoryBean`-Instanzen könnte subtile Fehler und schlechtere Leistung verursachen.
Versuchen Sie daher nicht, Axelix-Beans auszutauschen.

**Verlassen Sie sich nicht auf die öffentliche Java-API eines Starters.** Da Starter in realen Anwendungen laufen,
kann Ihr Code technisch auf diese API zugreifen. Das ist jedoch **nicht vorgesehen**, und wir raten ausdrücklich davon ab.
Um schnell und konkurrenzfähig zu bleiben, **können** wir auch diese öffentliche API ändern.
Wir versuchen dies unbedingt zu vermeiden, behalten uns notwendige Änderungen aber bei einer **Minor-Aktualisierung** vor.

:::tip[Fehlt eine Funktion? Erstellen Sie ein Issue, statt den Starter anzupassen]
Wenn Sie etwas benötigen oder eine Funktion fehlt, **verändern Sie nicht den Starter**.
Erstellen Sie ein Issue in unserem [GitHub-Issue-Tracker](https://github.com/axelixlabs/axelix/issues). Wir werden es prüfen.
Wenn wir Ihre gewünschte Funktion hinzufügen, erhalten Sie eine **Eigenschaft** zur Steuerung des Verhaltens:
einen stabilen, unterstützten Konfigurationsweg statt eines Bean-Overrides oder einer Codeabhängigkeit.
:::
