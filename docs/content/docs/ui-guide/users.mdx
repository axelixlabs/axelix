## Who can open this page

The **Users** link only appears for accounts that hold the `users:read` authority. By default, that authority is bundled
only with the built-in `SUPER_ADMIN` role — `ADMIN`, `EDITOR`, and `VIEWER` cannot see the link or load the page. See
[Roles and authorities](../setting-up-master-ui/authentication/authentication.mdx#roles-and-authorities) for the full
grant table.

The **Create User** button, and the edit and delete controls on the profile screen, additionally require the
`users:manage` authority, which is also reserved for `SUPER_ADMIN`.

## The users list

The top section gives you three ways to narrow the table:

- **Search** filters by username or email. The counter on the right of the search field shows `<matches> / <total>` so
  you can see how many users are currently visible compared to the full list.
- **Roles** — multi-select drop-down. Picking one or more roles keeps only users that have at least one of the selected
  roles.
- **Origin** — multi-select drop-down with two values: `LOCAL` and `OIDC`. Accounts created in Master appear as
  `LOCAL`. Accounts that sign in through OIDC appear as `OIDC` after their first successful browser sign-in, so the
  filter returns only OIDC users who have logged in at least once.

Below the filters, the table lists every visible user with these columns:

- **Username** — the login name used at the sign-in screen.
- **Email** — the email address attached to the account. May be blank.
- **Last login** — the timestamp of the most recent successful sign-in, formatted as `DD.MM.YYYY HH:mm`. Accounts that
  have never signed in show **Not logged in**.
- **Origin** — `LOCAL` for accounts created in Master, `OIDC` for accounts materialized by the OIDC sign-in flow.
- **Roles** — coloured tags for each role granted to the user (`ADMIN`, `EDITOR`, `VIEWER`).

Click any row to open the [User Profile](#user-profile) for that account.

## Creating a user

The **Create User** button is only rendered when local authentication is enabled in Master
(`axelix.master.auth.options.local.enabled=true`). It is hidden in OIDC-only deployments because new accounts there come
from the identity provider, not from the Axelix UI.

Clicking the button opens a modal with the following fields:

- **Username** — the login name. Must be unique.
- **Email** — optional. If you leave it blank, the account is stored without an email.
- **Password** — the initial password. The user can change it later from their profile.
- **Roles** — select one or more roles: `ADMIN`, `EDITOR`, and `VIEWER`. You can change the selection later from the profile.

A successful creation closes the modal, shows a **User created successfully** toast, and refreshes the list.

## User Profile

Selecting a row in the users list opens that account's profile with its account details and roles.

For a local account, choose **Edit user** to open the editing dialog. You can change the first name, last name,
username, email, and password. **Confirm** saves the fields together; **Cancel** discards the changes.

- **Username** — the login name. Editing it changes how the user signs in.
- **Email** — the email address. Saving an empty value clears the email on the account.
- **Password** — enter and confirm a new password to replace the current one. Leave it blank to keep the current
  password. The current password cannot be displayed because Master never stores it in clear text.

To update the assigned roles, choose **Change roles** in the **Roles** section. Select one or more of `ADMIN`,
`EDITOR`, and `VIEWER`, then choose **Confirm**. The user's effective permissions are the union of the authorities
those roles grant.

Below the card sit two action buttons:

- **Delete user** — opens a confirmation modal (**Are you sure you want to delete this user?**). Confirming removes the
  account immediately; the page navigates back to the users list and a **User deleted successfully** toast appears.
  There is no undo.
- **Access Log** — currently disabled. The control is reserved for an upcoming feature that will ship with Axelix
  Enterprise. Both the Access Log and Axelix Enterprise itself are still in development, so the button cannot be clicked
  today.

:::warning
The **Delete user** action is irreversible. The account is removed from the database — there is no soft-delete or
restore.
:::

## OIDC sessions

When OIDC is enabled, a successful browser sign-in creates or updates an `OIDC` user row in Master's database. Master
updates **Last login**, stores the email from the OIDC `userinfo` payload when one is present, and shows the account in
this table with origin `OIDC`.

On every OIDC sign-in, Master re-evaluates `axelix.master.auth.options.oauth2.role-attribute-path` and refreshes the
stored role assignment from that result. As a result, OIDC accounts do show up on this screen, but their effective role
still comes from your identity-provider mapping.

:::warning
If an OIDC username matches an existing non-OIDC account, Master rejects the sign-in instead of merging the identities.
Resolve the collision in the identity provider or rename the local account first.
:::

For the full picture of how authentication is wired, see
[Authentication](../setting-up-master-ui/authentication/authentication.mdx).
