---
title: 服务发现的工作原理
description: "Axelix Master 如何了解存在哪些 Spring Boot 实例并使其状态保持最新：既可以在 Kubernetes 中自行发现实例，也可以让每个实例自行注册。"
---

Master 只能显示和管理它已知的实例。它通过以下两种方式之一了解实例：由 Master 自行查找实例（自动发现），
或由实例向 Master 通告自身（自注册）。

## 两种发现方式

```text
┌─ Kubernetes cluster ─────────────────────────────┐
│                                                  │
│  ┌──────────────────┐    ┌──────────────────┐    │
│  │  orders-service  │    │ billing-service  │    │
│  └────────▲─────────┘    └─────────▲────────┘    │
│           │                        │             │     ┌────────────────────┐
│           └────────────┬───────────┘             │     │ inventory-service  │
│                        │                         │     │ (VM, Docker, ...)  │
│                        │  auto-discovery:        │     └─────────┬──────────┘
│                        │  Master finds the pods  │               │
│                        │  and polls them         │               │  self-registration:
│                ┌───────┴───────┐                 │               │  the service registers
│                │ Axelix Master │◀────────────────┼───────────────┘  once, then heartbeats
│                └───────────────┘                 │
│                                                  │
└──────────────────────────────────────────────────┘
```

这些图中的每个服务都是使用 Axelix 构建插件构建并运行 Axelix Starter 的 Spring Boot 应用程序。

|                | 自动发现                                        | 自注册                                                        |
|----------------|-------------------------------------------------|---------------------------------------------------------------|
| 由谁发起调用   | Master 调用服务                                 | 服务调用 Master                                               |
| 适用环境       | 仅 Kubernetes                                   | 服务能够访问 Master 的任何环境                                |
| 如何启用       | Master 上的 `axelix.master.discovery.auto.enabled` | 服务上的 `axelix.sbs.discovery.self-registration`          |

当 Master 与你的服务在同一个 Kubernetes 集群中运行时，自动发现无需在服务侧进行任何设置。
自注册则适用于其他所有情况，例如普通虚拟机、Docker Compose，或 Master 无法扫描的网络。

:::note[两种方式可同时使用]
发现方式是按服务选择的，而不是针对整个服务群统一选择。一个 Master 可以自动发现其 Kubernetes
集群中的服务，同时接受在其他位置运行的服务进行自注册。例如，三个在虚拟机上运行的应用程序可以自注册，
而集群中的每个服务则通过自动发现被发现。
:::

## 完整状态只传输一次，之后仅进行小量更新

<ReleasedInNotice version="1.3.0" />

从 Axelix 1.3.0 开始，两种方式都遵循同样的原则。Master 只接收一次实例的完整状态：
对于自注册，在注册请求中接收；对于自动发现，在首次调用 `axelix-metadata` 时接收。
此后，实例只发送频繁的小量更新：对于自注册，通过心跳发送；对于自动发现，通过响应
`axelix-ping` 发送。

每次更新有两个作用。首先，告知 Master 实例仍然存活。其次，携带随时间变化的少量信息：
实例的健康状况、堆使用量和事务统计信息，这样无需重新注册，新出现的问题事务也会显示在 Master 中。
下图展示了这一行为。

在 1.3.0 之前，Master 每次都会接收完整状态：每次自动发现扫描时，以及每次自注册心跳时。

## 自动发现

```text
 Axelix Master                  Kubernetes API                orders-service
       │                              │                              │
       │  which pods are there?       │                              │
       │─────────────────────────────▶│                              │
       │◀─────────────────────────────│                              │
       │                                                             │
       │  first scan: axelix-metadata                                │
       │────────────────────────────────────────────────────────────▶│
       │◀──────────────────────────────────────── full registration ─│
       │                                                             │
       │  every next scan (each minute by default): axelix-ping      │
       │────────────────────────────────────────────────────────────▶│
       │◀─────────────────────────────── health, heap, transactions ─│
```

首次调用返回完整注册信息：构建坐标、版本和 Axelix 收集的洞察信息。随后，该实例会显示在 Master 中。
Master 和服务上的签名密钥与算法必须匹配。

在初始探测期间，Master 尚不知道 Starter 的版本。它会发送一个兼容性格式的 JWT，其主体为
`AXELIX.MASTER`，并包含旧版 Starter 所需的传统声明。1.3 及更高版本的 Starter 接受 Master 身份，
并忽略这些额外声明。这一兼容格式计划在 1.6 中移除。

对于后续的 UI 和 MCP 调用，Master 会先检查用户的权限。对于 1.3 及更高版本的 Starter，
随后会发送一个短期有效的 `AXELIX.MASTER` 技术用户 JWT，其中不包含用户角色或权限。
旧版 Starter 则会收到使用传统权限名称重新签发的用户令牌，并仍由自身执行权限检查。

每次扫描都会替换自动发现实例的整个列表。因此，Kubernetes 不再报告的 Pod 会在下一次扫描时消失。
Master 无法访问的 Pod 也会从列表中移除，并在后续能够访问它的扫描中重新出现。

对于 Starter 版本低于 1.3.0 的实例，由于没有 `axelix-ping`，Master 会在每次扫描时读取完整的
`axelix-metadata`。

## 自注册

```text
 inventory-service                                     Axelix Master
         │                                                   │
         │  on startup: register (full description,          │
         │  actuator URL, instance name)                     │
         │──────────────────────────────────────────────────▶│  the instance appears
         │                                                   │
         │  every 15 s: heartbeat (health, heap,             │
         │  transactions)                                    │
         │──────────────────────────────────────────────────▶│
         │──────────────────────────────────────────────────▶│
         │                                                   │
         │  heartbeat after Master lost the instance         │
         │──────────────────────────────────────────────────▶│
         │◀─────────────────────────────── unknown instance ─│
         │  register again                                   │
         │──────────────────────────────────────────────────▶│
         │                                                   │
         ╳  the service stops, heartbeats stop               │
                                                             │  removed after 45 s
```

对于低于 1.3.0 的 Starter 版本，每次心跳都是一次完整注册。

如果 Master 重启时使用空数据库，或者因心跳缺失而移除了实例，Master 就可能丢失实例。
在这两种情况下，下一次心跳都会使服务重新注册，因此整个服务群会在一个心跳间隔内重新出现。
注册和心跳均使用共享 JWT 签名密钥进行签名；如果密钥不同，Master 会拒绝这些请求。

1.3 及更高版本的 Starter 使用技术用户 JWT 对这两种请求进行签名，其主体为 `AXELX.MANAGED_SERVICE`
（此拼写是传输协议标识符）。该 JWT 不包含角色或权限。Master 在这些端点上只接受受管服务身份。
它也接受旧版 Starter 使用的传统 `AXELIX.STARTER` 主体，这一兼容性别名计划在 1.6 中移除。

## 两种方式对 Master 的共同要求

发现机制只会让 Master 知道实例存在。每个 UI 页面、MCP 工具和操作（例如更改日志级别）
仍然是 Master 对服务的调用。因此，无论通过哪种方式发现服务，Master 都必须能够通过 HTTP
访问服务的 Actuator 端点。如果应用程序使用自身的安全机制保护 Actuator 端点，
请参阅[故障排查](../more/troubleshooting.mdx)，了解如何允许 Master 的调用通过。
