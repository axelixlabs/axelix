***Scheduled Tasks as presented in Axelix UI***

A `@Scheduled` task runs in the background, so nobody notices when it starts failing or slowing down until its side
effects go missing. This page shows every scheduled task of the application, how its recent runs went, and lets you
change its schedule without a redeploy.

Turning a task on or off, editing its trigger, and running it on demand require the `scheduled-tasks:write` authority,
granted by the built-in **EDITOR**, **ADMIN**, and **SUPER_ADMIN** roles. Users without this authority see the same
controls, but Axelix keeps them disabled and explains why in a tooltip on hover.

## What the page shows

The page lists the tasks grouped by trigger type:

- **Cron** tasks run at the times a cron expression describes, for example `0 0/15 9-17 * * MON-FRI`.
- **Fixed delay** tasks wait the given interval after each run ends, so runs never overlap.
- **Fixed rate** tasks start every given interval, counted from the start of the previous run.

You can search the list by class or method name. Next to each task, the page shows its success rate over the stored
runs, so a failing job stands out without opening it. A rate of 90% or more counts as healthy. Disabled tasks show
**OFF** instead of a rate.

When you select a task, the page shows its full class name and its schedule in plain words, such as "Every 3 seconds".
For a cron task, the expression itself appears next to the description.

## Execution history

<ReleasedInNotice version="1.3.0" />

Every run of a task is recorded, whether the schedule started it or you clicked **Run now**. Master collects the runs
from all instances of the application, so the history of a task is shared across instances. The summary covers all
stored runs:

- **Last run**: how long ago the latest run started.
- **Success**: the share of runs that finished without an exception.
- **Failed**: the number of runs that threw an exception.
- **Avg** and **p95**: the average run duration and the duration that 95% of runs fit into. A p95 far above the
  average means some runs get stuck now and then.

The **Duration** chart shows the last 30 runs from oldest to newest, with failed runs marked. The bar height is not
linear, so short runs stay visible next to a slow outlier. Hover a bar to see when the run started, how long it took,
and the error type if it failed.

When a task has failed, **Failures by error type** groups the failures by exception class, the most frequent first.
For each group, you see the latest error message and when it happened. This tells you at a glance whether one cause
keeps repeating or failures are unrelated.

The **Executions** table lists the same last 30 runs with the start time, the instance that ran the task, the duration,
and the result. Switch to **Failed** to see only the failed runs.

The history does not refresh on its own while the page is open. To see new runs, select the task again. Until Master
receives the first run of a task, the page shows **No execution data for this task** instead of the history.

### Execution history retention

Master keeps the history in its database and removes old runs on a schedule. These Master properties control how much
history it keeps (see also [Configuring
Master](../../setting-up-master-ui/configuring-master/configuring-master.mdx#scheduled-tasks-history)):

| Property                                                        | Default          | Description                                                                 |
|-----------------------------------------------------------------|------------------|-----------------------------------------------------------------------------|
| `axelix.master.scheduled-tasks.history.retention`               | `30d`            | How long Master keeps a run. Older runs are deleted on the next cleanup.     |
| `axelix.master.scheduled-tasks.history.max-executions-per-task` | `50`             | How many of the latest runs Master keeps for each task.                      |
| `axelix.master.scheduled-tasks.history.cleanup.schedule`        | `0 */10 * * * *` | The cron expression for the cleanup job. By default, it runs every 10 minutes. |

<Tabs groupId="spring-config" items={['application.properties', 'application.yaml']}>
  <Tab value="application.properties">

```properties
axelix.master.scheduled-tasks.history.retention=7d
axelix.master.scheduled-tasks.history.max-executions-per-task=100
```

  </Tab>
  <Tab value="application.yaml">

```yaml
axelix:
  master:
    scheduled-tasks:
      history:
        retention: 7d
        max-executions-per-task: 100
```

  </Tab>
</Tabs>

## Managing tasks

These actions apply to the instance you opened. Other instances of the same application keep their current state and
schedule.

### Enable or disable a task

Use the **ON** / **OFF** switch to stop a task from running on its schedule, for example while a downstream system is
under maintenance. Axelix asks for confirmation first. When you disable a task during a run, the run finishes, and then the task ignores its schedule.
Switch it back **ON** to resume the schedule.

### Edit the trigger

Click **Edit trigger** to change when the task runs. The new schedule takes effect immediately, without restarting the
application.

- For a cron task, enter a new expression with six fields: second, minute, hour, day, month, weekday. Axelix checks the
  expression as you type. The preview shows when the task will run (**Runs:**), or why the expression is wrong
  (**Invalid:**).
- For a fixed delay or fixed rate task, enter the new interval as a whole number of milliseconds above 0.

**Apply trigger** stays disabled until the value is valid and differs from the current one.

### Run a task now

Click **Run now** and confirm to run the task once, right away. This does not change its schedule, so it is useful to retry a
failed job or check a fix without waiting for the next scheduled run.

## Enable Dedicated Actuator Endpoint

<LegacyNotice
  version="1.2.0"
  reason={<>If you are on Axelix 1.2.0 or later, none of this is required: the starter registers its custom actuator
    endpoints by itself, and Axelix no longer requires the <code>health</code>/<code>info</code> endpoints to be
    enabled. It works perfectly well without them. No configuration is needed here.</>}
/>

The page is backed by the `axelix-scheduled-tasks` actuator endpoint contributed by the Axelix Spring Boot Starter.
Expose it through the standard Spring Boot Actuator properties. See [Configuring Spring Boot
Starter](../../setting-up-spring-boot-service/spring-boot-starter/configuration.mdx) for the full list
of Axelix endpoints and surrounding setup:

<Tabs groupId="spring-config" items={['application.properties', 'application.yaml']}>
  <Tab value="application.properties">

```properties
management.endpoints.web.exposure.include=axelix-scheduled-tasks
```

  </Tab>
  <Tab value="application.yaml">

```yaml
management:
  endpoints:
    web:
      exposure:
        include:
          - axelix-scheduled-tasks
```

  </Tab>
</Tabs>
