Chaque entrée présente le nom de l’outil, les annotations qu’il déclare, son état d’activation, les rôles autorisés à l’appeler et une brève description de son action. Le même catalogue est accessible dans le navigateur sur l’[écran MCP](../../ui-guide/mcp.mdx). Cette page constitue la liste de référence pour les opérateurs qui définissent qui peut appeler quels outils.

Cette liste suppose que le serveur MCP est activé (`axelix.master.mcp-server.enabled=true`, valeur par défaut). Lorsque cette propriété vaut `false`, le serveur n’est pas enregistré, aucun des outils ci-dessous n’est accessible et le lien **MCP** est masqué dans l’interface utilisateur. Consultez [Configuration du serveur MCP](../configuring-master/configuring-master.mdx#serveur-mcp).

## État des outils

Tous les outils ci-dessous sont intégrés à Master et enregistrés auprès du serveur MCP au démarrage. Aucun interrupteur ne permet d’activer ou de désactiver un outil individuellement : le catalogue est fixé lors du build. Un outil devient inaccessible uniquement lorsque le serveur MCP lui-même est désactivé ou que le processus Master n’est pas en cours d’exécution. Dans le [catalogue de l’interface utilisateur](../../ui-guide/mcp.mdx#le-catalogue-des-outils), le point d’état de chaque carte reflète cet enregistrement en temps réel : vert lorsque le serveur a enregistré l’outil, rouge lorsqu’il est indisponible.

## Annotations des outils

Chaque outil déclare quatre annotations booléennes qui indiquent aux clients MCP les effets de bord à prévoir. Les valeurs ci-dessous sont celles déclarées par les outils d’Axelix : ce sont des indications pour l’agent appelant, et non des contrôles d’autorisation appliqués par Master.

- **read-only** — l’outil ne modifie aucun état dans l’instance Spring Boot cible.
- **idempotent** — appeler plusieurs fois l’outil avec les mêmes arguments produit le même effet qu’un seul appel.
- **destructive** — l’outil peut supprimer des données ou appliquer des changements impossibles à annuler depuis l’interface utilisateur.
- **open-world** — l’outil accède à des ressources extérieures à Master et aux instances Spring Boot enregistrées.

## Contrôle par rôle

Le filtre MCP (`McpAuthorizationFilter`) authentifie l’agent de la même manière que l’interface utilisateur authentifie une session de navigateur. Consultez [Authentification du serveur MCP](../authentication/authentication.mdx#authentification-du-serveur-mcp) pour les mécanismes d’authentification.

## Catalogue

:::info
Le catalogue ci-dessous présente les outils MCP actuellement livrés avec Master. D’autres outils sont en cours de développement et la liste s’enrichira dans les prochaines versions.
:::

La colonne **Depuis** indique la version d’Axelix Master dans laquelle un outil a été livré pour la première fois. `1.0.0` étant la première version d’Axelix, un outil marqué `1.0.0` est présent depuis le début. Une version marquée _à venir_ n’est pas encore publiée : l’outil sera disponible dans la prochaine version d’Axelix, mineure ou majeure.

### Instances

L’unique outil de ce groupe renvoie le registre complet des instances Spring Boot gérées par Master. C’est le point d’entrée de toute tâche qui commence par « trouver le service par son nom et obtenir son `instanceId` » : tous les autres outils ont besoin de cet `instanceId`.

#### `getWallboard` est renommé en `getInstances`

<ReleasedInNotice version="1.3.0" />

Jusqu’à Axelix 1.2.x inclus, cet outil s’appelait `getWallboard`. À partir d’Axelix 1.3.0, il s’appelle `getInstances` et `getWallboard` n’existe plus. Son comportement, ses paramètres et sa réponse restent identiques.

Les agents IA découvrent les outils auprès du serveur MCP à la connexion et prennent donc automatiquement en compte le nouveau nom. Si vous appelez directement l’outil par son nom, par exemple depuis vos propres scripts ou des instructions destinées aux agents, remplacez `getWallboard` par `getInstances`.

### Analyse de la persistance

Problèmes de persistance détectés par Axelix dans la couche d’accès aux données d’une application. Contrairement aux outils précédents, ceux-ci utilisent les coordonnées de build de l’application — `groupId` et `artifactId` (le G et le A des coordonnées GAV), tous deux obligatoires — plutôt qu’un `instanceId`. Ils lisent l’instantané enregistré de l’application au lieu d’interroger une instance active.

Voir aussi : [Transaction Control](../../features/spring-framework/transaction-control.mdx).
