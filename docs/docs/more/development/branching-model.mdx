# Branching Model

Axelix is developed in the open as a monorepo, so understanding how the codebase evolves also explains
**why releases arrive the way they do**. This page describes the branches we use, how changes land, and
how that maps onto the [releases](../compatibility-and-versioning.mdx) you consume.

## The trunk

Axelix follows a **trunk-based development** model, with a couple of deliberate exceptions. There is one
main trunk: the **`master`** branch.

- Whenever we develop a new feature or a fix, we create a branch _from_ `master`.
- We merge it _back into_ `master` through a Pull Request.

`master` is always the source of truth for "what Axelix is right now". **Minor and major releases are cut
directly from it by tagging the trunk** with a tag of the form `vX.Y.0` — for example `v3.1.0`. The patch
component of a fleet tag is **always `0`**: a `vX.Y.0` tag marks the coordinated, whole-fleet cut in which
every component ships together under that one version (see
[how components are versioned](../compatibility-and-versioning.mdx#how-axelix-components-are-versioned)).
That single tag on `master` is the *only* thing a minor or major release is.

## Breaking changes

Not every finished change is merged immediately. If a change carries **breaking changes**, we do not merge
it into `master` as part of the normal flow. Instead we:

1. Postpone the Pull Request.
2. Label it `breaking-changes`.
3. Merge it later, when the time is right — typically when we begin working towards the next **major**
   version.

This keeps `master` **releasable as a minor or patch version at any time**, while breaking work waits for a
major-release boundary. It is a big part of why you can trust that a new **minor** never sneaks a breaking
change past you.

## Where patch work lives

Fixes for an already-released minor line do **not** go straight onto `master` for release. And unlike a
minor or major cut, a patch is **never** cut for the product as a whole — it is always cut for **one
specific component**: a single starter, a single plugin, or Master. So the first step is recognizing that a
particular component needs the fix, not the whole distribution; everything else stays exactly where it is.
This is the per-component half of the model — see
[how components are versioned](../compatibility-and-versioning.mdx#how-axelix-components-are-versioned) and,
for the reasoning,
[why patches are per component and not lockstep](../compatibility-and-versioning.mdx#why-patches-are-per-component-and-not-lockstep).

Once we know which component needs a patch, the flow is:

1. **Fork a component-specific patch branch off that minor's fleet tag.** The branch name encodes both the
   minor line and the component, following the pattern `X.Y.0-<component>` and forked from the `vX.Y.0`
   tag.

2. **Make the fix on that branch.** Only the code of that one component changes — the branch exists to carry
   this one component's patch, nothing else.

3. **Pin the component's version in its local `gradle.properties`.** Every releasable component carries its
   own `gradle.properties`. On the patch branch we set `axelixVersion` there to the new patch version.
   Because the build reads the *nearest* `gradle.properties` per component, this raises **only that
   component's** version; every other component keeps inheriting the fleet-wide `axelixVersion` from the
   repository root and is left untouched.

4. **Release that single component.** The one patched artifact is published, and the release is marked (by the
   release pipeline) with a component-specific tag that follows this pattern: `vX.Y.Z-<component>`, where `Z` is the
   patch version number.

Let's go through the simple example:

Imagine we need to create a patch for the Axelix Spring Boot 3 Starter released in the `3.1.0` Axelix release.
Such patches *must* live on a branch named `3.1.0-sbs3`, and that branch *must* forked from `v3.1.0` git tag (the tag for
the `3.1.0` Axelix release). If we have already released patches for the Axelix Spring Boot 3 Starter released in the `3.1.0`,
then branch `3.1.0-sbs3` should've obviously existed before.

Once we applied the necessary patches, we modify the local `gradle.properties` file for that specific gradle sub-project.
In particular, we specify version `3.1.1`, since this is the patch version we want to release.

Then we launch a release pipeline, that is in turn going to create the tag named
`v3.1.1-sbs3` (again, pattern `vX.Y.Z-<component>`) and release the patch for that specific component, whether it is the Maven
Artifact, Docker Image or Helm Chart - does not matter, the release pipeline will handle that.

:::note[Patch branches exists per-component]
I would like to empathize - each patch branch exists **per individual component**.
It means that patches for the Axelix Master, for example, will live in the dedicated branch names `3.1.0-master`,
which is also forked from the `3.1.0` git tag. The patches for the Maven Plugin will live in the separate patch
branch - `3.1.0-maven`.
:::

The result is the **ragged** set of patch numbers described in
[how components are versioned](../compatibility-and-versioning.mdx#how-axelix-components-are-versioned) —
Master may sit at `3.1.4` while a starter is still `3.1.1` and a plugin never left `3.1.0`. They stay
compatible the entire time, because
[compatibility is guaranteed by `major.minor`](../compatibility-and-versioning.mdx#compatibility-between-components),
whatever the patch numbers happen to be.
