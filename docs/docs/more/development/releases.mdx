# Releases

This page describes the **exact procedure** by which we release Axelix. There are two kinds of release,
and they share the same shape at different scope:

- A **minor** release ships the **whole fleet** at once, cut from `master`.
- A **patch** release ships **one component** on its own, cut from that component's patch branch.

Of course, we're going to have a major release as well. When it comes to major release as well - we'll document it also.

For the branch layout underneath all of this see [Branching Model](./branching-model.mdx).

## Minor releases

A minor release publishes every component together under a single `X.Y.0` version and marks it
with a `vX.Y.0` tag on `master` (see
[how components are versioned](../compatibility-and-versioning.mdx#how-axelix-components-are-versioned)). The
procedure, in order:

### 1. Housekeeping

Housekeeping is the set of **manual changes** made before the release. They all go into a **single commit on
`master`**, so the whole release can be reset or cherry-picked cleanly if we have to postpone it.

- **Set the fleet version.** Set `axelixVersion` in the **root** `gradle.properties` to the exact version we
  are releasing — for `3.1.0`, set it to `3.1.0`. This is the value the release pipeline reads and what the
  resulting tag is named after. In the master trunk, the local `gradle.properties` will never contain the `axelixVersion`,
  thus they all will take the version of Axelix from the root `gradle.properties`.
- **Bump the playgrounds.** The example apps under `playgrounds/` are, by design, **separate projects** — they
  do **not** inherit `axelixVersion`, they pin the Axelix starter and plugin versions they consume explicitly.
  Bump those pinned versions to the version being released.
- **Update the documentation.** We keep versioned docs per **major** line only. For example, while a minor is in
  development we add "upcoming release" notices for the features it will ship; when we cut the minor that
  actually ships them, those notices are replaced with the corresponding "released in" notices.

### 2. Launch the release pipeline

**We do not create the tag by hand.** The release pipeline reads the version from `gradle.properties`, runs
its pre-release checks, and only if everything is green does it create the `vX.Y.0` tag and publish every
component of the fleet.

:::info[Release notes are written by hand]
The pipeline creates the **tag** — it does **not** write the release notes. Composing the release notes for the
freshly created `vX.Y.0` tag is left to the **developer** cutting the release, who writes them manually against
that tag.
:::

:::note[Major releases]
A major release is cut **exactly the same way**. The one addition is that the held-back breaking-change work
(see [Branching Model → Breaking changes](./branching-model.mdx#breaking-changes)) is merged into `master`
first, before housekeeping.
:::

## Patch releases

A patch is **never** cut for the product as a whole — it is always cut for **one specific component**: a
single starter, a single plugin, or Master. So the first step is recognizing that a particular component
needs the fix, not the whole distribution; everything else stays exactly where it is. (This is the
per-component half of the model — see
[why patches are per component and not lockstep](../compatibility-and-versioning.mdx#why-patches-are-per-component-and-not-lockstep).)

The procedure mirrors a minor release, with two differences: it is cut from the component's **patch branch**
instead of `master`, and the version is pinned **locally** so only that one component moves. The
documentation step is skipped — patches do not change the docs.

1. **Check out the component's patch branch.** Patch work lives on a per-component branch named
   `X.Y.x-<component>` — the literal `x` marks it as the whole patch line, and, unlike a tag, the branch name
   carries **no** `v` prefix. It is forked from the minor's `vX.Y.0` tag (see
   [Branching Model → Where patch work lives](./branching-model.mdx#where-patch-work-lives)). Create it from
   the tag if this is that component's first patch on the line; otherwise it already exists.

2. **Make the fix on that branch.** Only the code of that one component changes.

3. **Housekeeping on the branch (single commit).**
   - **Pin the component's version.** Set `axelixVersion` in that component's **own** `gradle.properties` to
     the new patch version. Because the build reads the *nearest* `gradle.properties` per component, this
     raises **only that component's** version; every other component keeps inheriting the fleet-wide
     `axelixVersion` from the repository root and is untouched.
   - **Bump the playground(s).** Update the playground apps that consume the patched component to the new
     patch version — same reason as for a minor release: playgrounds pin their Axelix versions explicitly and
     do not inherit `axelixVersion`.

4. **Launch the release pipeline.** It publishes the single patched artifact and creates a component-specific
   tag `vX.Y.Z-<component>`, where `Z` is the new patch number. Like every Axelix tag it carries the `v`
   prefix. As with a minor release, the pipeline creates the tag but **not** the release notes — the developer
   writes those manually against the new tag.

### Worked example

Say we need to patch the **Axelix Spring Boot 3 Starter** from the `3.1.0` release:

1. The patch lives on the branch `3.1.x-sbs-3`, forked from the `v3.1.0` tag. If the starter has been patched
   on this line before, that branch already exists; otherwise we create it from `v3.1.0`.
2. We apply the fix on that branch.
3. In that starter's own `gradle.properties` we set `axelixVersion` to `3.1.1` — the patch version we want to
   release — and bump the Spring Boot 3 playground(s) to `3.1.1`.
4. We launch the release pipeline. It creates the tag `v3.1.1-sbs-3` and publishes the patched starter —
   whether the deliverable is a Maven artifact, a Docker image, or a Helm chart, the pipeline handles it.

The result is the **ragged** set of patch numbers described in
[how components are versioned](../compatibility-and-versioning.mdx#how-axelix-components-are-versioned) —
Master may sit at `3.1.4` while a starter is still `3.1.1` and a plugin never left `3.1.0`. They stay
compatible the entire time, because
[compatibility is guaranteed by `major.minor`](../compatibility-and-versioning.mdx#compatibility-between-components),
whatever the patch numbers happen to be.
