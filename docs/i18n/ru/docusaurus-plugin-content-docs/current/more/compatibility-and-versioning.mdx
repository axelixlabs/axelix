# Совместимость и версионирование

На этой странице описано, как версионируется сам Axelix и как он остаётся совместимым с основными участниками процесса:
версией **Java**, на которой работают ваши сервисы, мажорной версией **Spring Boot**, под которую они собраны, и как
собственные компоненты Axelix остаются совместимыми **друг с другом**.

## Как версионируются компоненты Axelix

Axelix использует **гибридную** модель версионирования, которую проще всего понять в двух частях.

**Мажорные и минорные версии двигаются синхронно (lockstep).** Когда выпускается новая минорная или мажорная линия —
скажем, **Axelix 3.1.0** — *каждый* компонент выходит одновременно под этой же версией `3.1.0`:

- **Spring Boot-стартеры** (публикуются как Maven-артефакты);
- **плагины** (тоже публикуются как Maven-артефакты);
- **Axelix Master** как standalone JAR;
- **Axelix Master** как Docker-образ;
- **Helm-чарт Axelix Master**.

Минорный/мажорный релиз — это единый, согласованный выпуск всего дистрибутива: весь «флот» переходит на `3.1.0` разом.

**Патч-версии двигаются по каждому компоненту отдельно.** После выхода минорной линии отдельные компоненты получают
патчи независимо. Исправление критической CVE, фикс бага или улучшение производительности в одном компоненте выходит
как патч *только этого компонента* — остальные остаются на месте. Поэтому внутри одной минорной линии вы регулярно
будете видеть **неровный** набор патч-версий:

- Master `3.1.2`, тогда как стартеры всё ещё `3.1.0`;
- стартер `3.1.3`, тогда как Master всё ещё `3.1.0`, а плагин так и не ушёл дальше `3.1.0`.

Нет правила, что для каждого компонента существует конкретный номер патча — стартер `3.1.1` может просто никогда не
выйти.

:::info[Единственное, что имеет значение — это `major.minor`]
Вам никогда не нужна матрица совместимости. Всё, что разделяет одну и ту же пару **`major.minor`**, совместимо — какими
бы ни были номера патчей (см. [Совместимость между компонентами](#совместимость-между-компонентами) ниже).
:::

### Почему патчи выпускаются по компонентам, а не синхронно

Было бы проще сказать «все компоненты всегда имеют ровно одну и ту же версию» — и именно так мы и делаем для **минорных
и мажорных** релизов. Так почему не для патчей тоже?

Потому что поток патчей непрерывен и в основном приходит **извне** нашего собственного кода. Посмотрите, что заставляет
выпускать патч:

- CVE в **базовом Docker-образе** → нам нужно опубликовать новый Docker-образ **Axelix Master**.
- CVE в **транзитивной библиотеке** на classpath у Master → нам нужно опубликовать новый JAR **Axelix Master** (а также
  образ и Helm-чарт).
- Фикс бага или улучшение производительности в одном стартере.

Ни одно из этого не имеет никакого отношения к стартерам или плагинам. Но при строгом lockstep *каждый такой случай*
вынуждал бы нас перевыпускать стартеры и плагины синхронно — поднимая их до новой патч-версии, которая **побайтово
идентична** предыдущей. За время жизни одной минорной линии это легко складывается в **десятки** патч-релизов, и для
стартера или плагина подавляющее большинство из них несло бы **ноль** реальных изменений.

Это плохо для нас и ещё хуже для вас:

- Обновления зависимостей превращаются в шум. Новый патч `axelix-spring-boot-3-starter` появлялся бы в вашей сборке
  постоянно, и почти всегда в нём ничего бы не менялось.
- Вы никогда не смогли бы отличить осмысленный фикс стартера от подъёма версии, который существует лишь для того, чтобы
  держать «флот» синхронным.

Выпуск патчей **по компонентам** решает обе проблемы. Master может поглощать свой поток CVE из базового образа и
транзитивных зависимостей на собственной патч-линии, никого за собой не таща. А когда вы *всё же* видите новый патч
стартера или плагина — значит, этот компонент действительно изменился и обновление заслуживает вашего внимания. Контракт
`major.minor` — это то, что позволяет нам делать это безопасно: компоненты остаются совместимыми всё это время, как бы
далеко ни разошлись их номера патчей.

## Отдельный стартер под каждую мажорную версию Spring Boot

Axelix поставляет **отдельный стартер под каждую мажорную версию Spring Boot**. Для каждой поддерживаемой мажорной
версии существует самостоятельный, отдельный артефакт:

- `axelix-spring-boot-2-starter` — для сервисов на Spring Boot **2.x**;
- `axelix-spring-boot-3-starter` — для сервисов на Spring Boot **3.x**;
- `axelix-spring-boot-4-starter` — для сервисов на Spring Boot **4.x**.

На данный момент Axelix поддерживает Spring Boot **мажорных версий с 2 по 4**. Выбирайте стартер, соответствующий
мажорной версии Spring Boot вашего сервиса.

С **плагинами** ситуация иная: они спроектированы максимально универсальными, поэтому выбирать артефакт под конкретную
версию не нужно:

- **Gradle-плагин** протестирован на мажорных версиях Gradle **с 5 по 9**;
- **Maven-плагин** совместим с **Maven 3** (именно его сегодня использует практически любой Maven-проект, так что всё хорошо).

## Совместимость с версиями Java

**Axelix Master** — это сам по себе Spring Boot-приложение, написанное на **Java 25**. Это важно только в случае, если вы
хотите запускать Axelix Master как JAR. В любом другом случае разницы нет.

**Стартеры** следуют совместимости по Java той версии Spring Boot, под которую они собраны. Каждый стартер совместим с
**любой версией Java, которая поддерживается данной мажорной версией Spring Boot**. Например, Spring Boot 3 поддерживает
как минимум Java **17** и вплоть до Java **25** (в Spring Boot 3.5) — и `axelix-spring-boot-3-starter` следует ровно тому же диапазону.
Он тоже тестируется на всех версиях от Java 17 до Java 25.

:::info[Минимальная версия Java — 11]
Единственное исключение из правила «следуем за поддержкой Java у Spring Boot» — это жёсткий **минимум Java 11** для
**стартеров и плагинов** Axelix. Пользователи Spring Boot 2, которые теоретически ещё могут быть на **Java 8**, не смогут
использовать Axelix — им нужно обновиться как минимум до **Java 11**.
:::

## Совместимость между компонентами

Есть одно-единственное правило, и оно применимо к **любому** компоненту Axelix:

> **Любые два компонента Axelix гарантированно совместимы до тех пор, пока они разделяют одну и ту же **мажорную** и
> **минорную** версию. Патч-версия значения не имеет.**

Это весь контракт. Он покрывает сразу все сочетания — Master со стартером, стартер со своим плагином, все вместе — так
что матрица совместимости вам не нужна. Просто выровняйте `major.minor`.

- ✅ Master `1.4.2`, стартер `1.4.5`, плагин `1.4.0` — все на `1.4`, гарантированно совместимы.
- ✅ Стартер `1.4.3` с плагином `1.4.0` — одна и та же `1.4`, гарантированно совместимо.
- ⚠️ Master `1.4.2` со стартером `1.3.4` — **минорное расхождение**, не гарантируется. Может сработать, может сломаться.
- ⚠️ Стартер `3.1.x` с плагином `3.3.x` — **минорное расхождение**, не гарантируется и не поддерживается.
- ⚠️ Любое **мажорное** расхождение — не гарантируется и ещё менее вероятно сработает, чем минорное.

Если компоненты расходятся на **минорной** или **мажорной** версии, мы не гарантируем **ничего** — комбинация **может**
сработать, но **может** и сломаться, и она не тестируется.

### Почему патч-расхождение безопасно, а минорное/мажорное — нет

В основе этой политики лежит предположение, что **вся функциональность, которую предоставляют компоненты, предназначена
для доступа через веб-интерфейс Axelix Master**. Нет сценария, в котором вам понадобилось бы поднимать **минорную**
версию отдельного компонента саму по себе, чтобы получить какую-то возможность — эта возможность проявляется через
Master, а не через компонент в отрыве от него. Поэтому мы позволяем себе **пересматривать контракты между компонентами в
минорных релизах**, что позволяет проекту двигаться быстро.

С патч-релизами всё иначе. Как гласит [semver](https://semver.org/), патч-релиз может нести **критический фикс CVE,
исправление бага или улучшение производительности** — и эти изменения ценны **сами по себе**. Так что патч-расхождение —
это то, чего вы можете действительно хотеть, и мы гарантируем, что оно остаётся совместимым.

:::warning[Минорное и мажорное расхождение может сломать протоколы взаимодействия]
Мы **можем** — это **не** значит, что мы **будем**, но мы **можем** — пересматривать протоколы между компонентами
(Master ↔ стартер, плагин ↔ стартер) между **минорными** релизами, не говоря уже о **мажорных**. Это значит, что любая
комбинация, пересекающая минорную границу, **может** сломаться. Это не значит, что она **сломается** — но она **может**, и
обратного мы не гарантируем. Держите каждый компонент на одной мажорной **и** минорной версии, и позволяйте расходиться
только патч-версиям.
:::

## Гарантии обратной совместимости между релизами

### Axelix Master

Axelix Master — это Java-приложение, которое предполагается **запускать как самостоятельный процесс**: в Kubernetes, в
Docker или просто как JAR. Использовать его **как библиотеку не предполагается**. Поэтому мы **не** считаем публичную
поверхность Java публичным контрактом: **публичные классы, публичные методы, конструкторы, поля, enum-ы и константы —
всё это считается внутренним**.

На практике это значит, что мы можем менять этот публичный Java API в **минорных и даже патч**-релизах. Предполагается,
что никто не зависит от Master как от библиотеки, поэтому свобода менять его Java API позволяет нам **разрабатывать
быстрее**. Это осознанный компромисс, который реально почти никого не затрагивает — большой плюс для темпа развития
проекта.

А вот что мы **считаем** публичным контрактом Master — это его **конфигурацию**:

- **имена** свойств — как для **Helm-чарта** Axelix Master, так и для запуска Axelix Master как **standalone JAR**;
- их **значения по умолчанию**;
- их **типы**.

Всё это будет меняться **только в мажорных релизах**.

:::info[Правило для Master]
Полагайтесь на **свойства** Master (имена, значения по умолчанию, типы) — они стабильны в пределах мажорной версии. Не
полагайтесь на Java-классы, методы и прочие элементы уровня кода в Master — они могут меняться в любом релизе.
:::

### Стартеры

Стартеры **действительно** используются как библиотеки — это Spring Boot-стартеры, поэтому они приносят в ваше
приложение auto-configuration'ы с бинами (bootstrap-обвязку, внутреннюю стратегию проксирования и так далее). Из этой
реальности вытекают два правила.

**Не переопределяйте бины Axelix.** Мы намеренно **не** даём конечным пользователям переопределять внутренние бины,
которые объявляет Axelix, чтобы вмешиваться в процесс bootstrap, стратегию проксирования и подобные внутренности. Это
осознанный выбор. Axelix изо всех сил старается не добавлять **никакого ощутимого оверхеда** вашему приложению и быть
максимально эффективным и стабильным; возможность переопределять бины вроде `BeanPostProcessor`-ов или экземпляров
`ProxyFactoryBean` открыла бы backdoor для трудноуловимых багов и худшей производительности. Поэтому, пожалуйста, не
пытайтесь подменять бины Axelix. С огромной вероятностью вы не сделаете лучше - вы сделаете хуже.

**Не завязывайтесь на публичный Java API стартера.** Приходится признать, что стартеры работают внутри реальных
приложений, поэтому их публичный Java API технически *можно* использовать из вашего кода — но это **не предполагается**,
и мы настоятельно не советуем так делать. Чтобы двигаться быстро и оставаться конкурентоспособными, мы **можем** менять
публичный Java API и в стартерах. Мы будем избегать этого любой ценой, но если сочтём необходимым — можем изменить его
в рамках **минорного** апгрейда версии.

:::tip[Не хватает возможности? Заведите issue, а не тинкерите]
Правило простое: если вам чего-то не хватает или нужна какая-то возможность — **не тюнтье стартер**, а заведите
issue в нашем [трекере на GitHub](https://github.com/axelixlabs/axelix/issues). Мы обещаем, что рассмотрим. Когда мы
добавим запрошенную вами возможность, мы дадим вам **свойство** для управления этим поведением — стабильную,
поддерживаемую настрокйу, а не переопределение бина или зависимость на уровне кода.
:::
