# Релизы

Эта страница описывает **точную процедуру**, по которой мы выпускаем Axelix. Есть два вида релизов, и у них
одинаковая форма, но разный масштаб:

- **Минорный или мажорный** релиз выпускает **весь флот** сразу, срезаясь из `master`.
- **Патч**-релиз выпускает **один компонент** отдельно, срезаясь из патч-ветки этого компонента.

Про раскладку веток под всем этим — trunk, обработку ломающих изменений и патч-ветки на каждый компонент —
см. [Модель ветвления](./branching-model.mdx).

## Минорные и мажорные релизы

Минорный или мажорный релиз публикует каждый компонент вместе под одной версией `X.Y.0` и помечает его тегом
`vX.Y.0` на `master` (см.
[как версионируются компоненты](../compatibility-and-versioning.mdx#как-версионируются-компоненты-axelix)).
Процедура, по порядку:

### 1. Housekeeping

Housekeeping — это набор **ручных изменений**, которые делаются перед релизом. Все они идут **одним коммитом в
`master`**, чтобы весь релиз можно было чисто откатить или перенести (cherry-pick), если придётся его отложить.

- **Задаём версию флота.** Ставим `axelixVersion` в **корневом** `gradle.properties` равным точной версии,
  которую выпускаем — для `3.1.0` ставим `3.1.0`. Именно это значение читает релизный пайплайн, и по нему
  называется итоговый тег.
- **Обновляем версии в playground-ах.** Примеры приложений под `playgrounds/` по своей природе **отдельные
  проекты** — они **не** наследуют `axelixVersion`, а явно фиксируют версии стартеров и плагинов Axelix, которые
  используют. Поднимаем эти зафиксированные версии до выпускаемой.
- **Обновляем документацию.** Мы ведём версионированную документацию только по **мажорным** линиям. Пока минор в
  разработке, мы добавляем пометки «в предстоящем релизе» для фич, которые он принесёт; когда режем минор,
  который эти фичи реально выпускает, эти пометки заменяются на соответствующие «выпущено в».

### 2. Запускаем релизный пайплайн

**Мы не создаём тег вручную.** Релизный пайплайн читает версию из `gradle.properties`, прогоняет свои
предрелизные проверки и только если всё зелёное — создаёт тег `vX.Y.0` и публикует каждый компонент флота.

:::note[Мажорные релизы]
Мажорный релиз режется **ровно так же**. Единственное дополнение — придержанная работа с ломающими изменениями
(см. [Модель ветвления → Ломающие изменения](./branching-model.mdx#ломающие-изменения)) сначала вливается в
`master`, до housekeeping.
:::

## Патч-релизы

Патч **никогда** не режется для продукта целиком — он всегда режется для **одного конкретного компонента**:
отдельного стартера, отдельного плагина или Master. Поэтому первый шаг — осознать, что фикс нужен именно
определённому компоненту, а не всему дистрибутиву; всё остальное остаётся ровно там, где было. (Это
по-компонентная половина модели — см.
[почему патчи выпускаются по компонентам, а не синхронно](../compatibility-and-versioning.mdx#почему-патчи-выпускаются-по-компонентам-а-не-синхронно).)

Процедура повторяет минорный релиз с двумя отличиями: срез делается из **патч-ветки** компонента, а не из
`master`, и версия фиксируется **локально**, так что двигается только этот один компонент. Шаг с документацией
пропускается — патчи не меняют документацию.

1. **Переключаемся на патч-ветку компонента.** Патч-работа живёт в ветке на каждый компонент с именем
   `X.Y.0-<компонент>`, ответвлённой от тега `vX.Y.0` этого минора (см.
   [Модель ветвления → Где живёт патч-работа](./branching-model.mdx#где-живёт-патч-работа)). Создаём её из
   тега, если это первый патч компонента на этой линии; иначе она уже существует.

2. **Делаем фикс в этой ветке.** Меняется код только этого одного компонента.

3. **Housekeeping в ветке (одним коммитом).**
   - **Фиксируем версию компонента.** Ставим `axelixVersion` в **собственном** `gradle.properties` этого
     компонента равным новой патч-версии. Поскольку сборка читает *ближайший* `gradle.properties` для каждого
     компонента, это поднимает версию **только этого** компонента; все остальные продолжают наследовать
     общефлотовый `axelixVersion` из корня репозитория и остаются нетронутыми.
   - **Обновляем playground(-ы).** Поднимаем те playground-приложения, которые используют пропатченный
     компонент, до новой патч-версии — по той же причине, что и при минорном релизе: playground-ы фиксируют
     свои версии Axelix явно и не наследуют `axelixVersion`.

4. **Запускаем релизный пайплайн.** Он публикует один пропатченный артефакт и создаёт тег под конкретный
   компонент `vX.Y.Z-<компонент>`, где `Z` — новый номер патча.

### Разбор на примере

Допустим, нам нужно пропатчить **Axelix Spring Boot 3 Starter** из релиза `3.1.0`:

1. Патч живёт в ветке `3.1.0-sbs3`, ответвлённой от тега `v3.1.0`. Если стартер уже патчился на этой линии, ветка
   уже существует; иначе создаём её из `v3.1.0`.
2. Применяем фикс в этой ветке.
3. В собственном `gradle.properties` этого стартера ставим `axelixVersion` равным `3.1.1` — патч-версии, которую
   хотим выпустить — и поднимаем playground(-ы) Spring Boot 3 до `3.1.1`.
4. Запускаем релизный пайплайн. Он создаёт тег `v3.1.1-sbs3` и публикует пропатченный стартер — будь то
   Maven-артефакт, Docker-образ или Helm-чарт, пайплайн об этом позаботится.

В результате получается **рваный** набор номеров патчей, описанный в разделе
[как версионируются компоненты](../compatibility-and-versioning.mdx#как-версионируются-компоненты-axelix) —
Master может быть на `3.1.4`, пока стартер всё ещё `3.1.1`, а плагин так и не ушёл с `3.1.0`. Всё это время они
остаются совместимыми, потому что
[совместимость гарантируется парой `major.minor`](../compatibility-and-versioning.mdx#совместимость-между-компонентами),
какими бы ни оказались номера патчей.
