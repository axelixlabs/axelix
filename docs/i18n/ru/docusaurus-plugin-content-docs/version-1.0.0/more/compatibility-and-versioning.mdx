# Совместимость и версионирование

На этой странице описано, как версионируется сам Axelix и как он остаётся совместимым с основными участниками процесса:
версией **Java**, на которой работают ваши сервисы, мажорной версией **Spring Boot**, под которую они собраны, и
связкой **Axelix Master** ↔ **Spring Boot Starter**.

## Одна версия для всех компонентов

Axelix выпускается как единый, согласованный дистрибутив. Все компоненты имеют **ровно одну и ту же версию**.

Когда выходит новый дистрибутив Axelix — скажем, **Axelix OSS 3.1.2** — каждый выпущенный компонент несёт эту же
версию `3.1.2`:

- **Spring Boot-стартеры** (публикуются как Maven-артефакты);
- **плагины** (тоже публикуются как Maven-артефакты);
- **Axelix Master** как standalone JAR;
- **Axelix Master** как Docker-образ.

Независимого версионирования по компонентам нет. Если вы знаете версию одного артефакта Axelix, вы знаете версию их
всех в этом релизе.

## Отдельный стартер под каждую мажорную версию Spring Boot

Axelix поставляет **отдельный стартер под каждую мажорную версию Spring Boot**. Для каждой поддерживаемой мажорной
версии существует самостоятельный, отдельный артефакт:

- `axelix-spring-boot-2-starter` — для сервисов на Spring Boot **2.x**;
- `axelix-spring-boot-3-starter` — для сервисов на Spring Boot **3.x**;
- `axelix-spring-boot-4-starter` — для сервисов на Spring Boot **4.x**.

На данный момент Axelix поддерживает Spring Boot **мажорных версий с 2 по 4**. Выбирайте стартер, соответствующий
мажорной версии Spring Boot вашего сервиса.

С **плагинами** ситуация иная: они спроектированы максимально универсальными, поэтому выбирать артефакт под конкретную
версию не нужно:

- **Gradle-плагин** протестирован на мажорных версиях Gradle **с 5 по 9**;
- **Maven-плагин** совместим с **Maven 3** (именно его сегодня использует практически любой Maven-проект, так что всё хорошо).

## Версии стартера и плагина должны совпадать

В рамках одного сервиса **стартер** и **плагин**, которые вы подключаете, **должны быть ровно одной версии**. Это
следует из правила [одна версия для всех компонентов](#одна-версия-для-всех-компонентов) — они выходят из одного релиза
Axelix, поэтому держите их синхронно.

:::danger[Не смешивайте версии стартера и плагина]
Мы **не** гарантируем, что стартер версии `3.1.2` будет работать с плагином версии `3.3.1`. Это **может** сработать, но
такая комбинация **не тестируется** и не поддерживается. Всегда фиксируйте стартер и плагин на одной и той же версии.
:::

## Совместимость с версиями Java

**Axelix Master** — это сам по себе Spring Boot-приложение, написанное на **Java 25**. Это важно только в случае, если вы
хотите запускать Axelix Master как JAR. В любом другом случае разницы нет.

**Стартеры** следуют совместимости по Java той версии Spring Boot, под которую они собраны. Каждый стартер совместим с
**любой версией Java, которая поддерживается данной мажорной версией Spring Boot**. Например, Spring Boot 3 поддерживает
как минимум Java **17** и вплоть до Java **25** (в Spring Boot 3.5) — и `axelix-spring-boot-3-starter` следует ровно тому же диапазону.
Он тоже тестируется на всех версиях от Java 17 до Java 25.

:::info[Минимальная версия Java — 11]
Единственное исключение из правила «следуем за поддержкой Java у Spring Boot» — это жёсткий **минимум Java 11** для
**стартеров и плагинов** Axelix. Пользователи Spring Boot 2, которые теоретически ещё могут быть на **Java 8**, не смогут
использовать Axelix — им нужно обновиться как минимум до **Java 11**.
:::

## Как понять, совместим ли Master с конкретным стартером

Правило простое:

> **Axelix Master совместим с сервисом до тех пор, пока у него та же _мажорная_ версия, что и у стартера этого сервиса.**

Если у Axelix Master и у стартера в сервисе **X** одинаковая **МАЖОРНАЯ** версия, Master будет работать с сервисом X.
Некоторые возможности, которые сервис X мог бы предложить, могут отсутствовать, но тем не менее сервис **обнаружится корректно** —
Master остаётся работоспособным и просто не показывает те возможности, которые более старый стартер не поддерживает.

Например, если у Axelix Master версия `3.6.1`, а у стартера в сервисе X — `3.1.2`, стартеру может не хватать части
новых возможностей. Master не сможет использовать именно эти возможности для сервиса X, но всё остальное работает как
ожидается.

:::warning[Расхождение версий допустимо, но не рекомендуется]

Расхождение на уровне **минорной** или **патч**-версии допустимо, но это **не лучшая практика**. Оно существует прежде
всего ради патчей безопасности, исправлений багов и улучшений производительности на стороне стартера. Держите стартеры
и Master на одной версии, где это возможно, и считайте совпадение **мажорной** версии жёстким требованием совместимости.
:::

## Гарантии обратной совместимости между релизами

### Axelix Master

Axelix Master — это Java-приложение, которое предполагается **запускать как самостоятельный процесс**: в Kubernetes, в
Docker или просто как JAR. Использовать его **как библиотеку не предполагается**. Поэтому мы **не** считаем публичную
поверхность Java публичным контрактом: **публичные классы, публичные методы, конструкторы, поля, enum-ы и константы —
всё это считается внутренним**.

На практике это значит, что мы можем менять этот публичный Java API в **минорных и даже патч**-релизах. Предполагается,
что никто не зависит от Master как от библиотеки, поэтому свобода менять его Java API позволяет нам **разрабатывать
быстрее**. Это осознанный компромисс, который реально почти никого не затрагивает — большой плюс для темпа развития
проекта.

А вот что мы **считаем** публичным контрактом Master — это его **конфигурацию**:

- **имена** свойств — как для **Helm-чарта** Axelix Master, так и для запуска Axelix Master как **standalone JAR**;
- их **значения по умолчанию**;
- их **типы**.

Всё это будет меняться **только в мажорных релизах**.

:::info[Правило для Master]
Полагайтесь на **свойства** Master (имена, значения по умолчанию, типы) — они стабильны в пределах мажорной версии. Не
полагайтесь на Java-классы, методы и прочие элементы уровня кода в Master — они могут меняться в любом релизе.
:::

### Стартеры

Стартеры **действительно** используются как библиотеки — это Spring Boot-стартеры, поэтому они приносят в ваше
приложение auto-configuration'ы с бинами (bootstrap-обвязку, внутреннюю стратегию проксирования и так далее). Из этой
реальности вытекают два правила.

**Не переопределяйте бины Axelix.** Мы намеренно **не** даём конечным пользователям переопределять внутренние бины,
которые объявляет Axelix, чтобы вмешиваться в процесс bootstrap, стратегию проксирования и подобные внутренности. Это
осознанный выбор. Axelix изо всех сил старается не добавлять **никакого ощутимого оверхеда** вашему приложению и быть
максимально эффективным и стабильным; возможность переопределять бины вроде `BeanPostProcessor`-ов или экземпляров
`ProxyFactoryBean` открыла бы backdoor для трудноуловимых багов и худшей производительности. Поэтому, пожалуйста, не
пытайтесь подменять бины Axelix. С огромной вероятностью вы не сделаете лучше - вы сделаете хуже.

**Не завязывайтесь на публичный Java API стартера.** Приходится признать, что стартеры работают внутри реальных
приложений, поэтому их публичный Java API технически *можно* использовать из вашего кода — но это **не предполагается**,
и мы настоятельно не советуем так делать. Чтобы двигаться быстро и оставаться конкурентоспособными, мы **можем** менять
публичный Java API и в стартерах. Мы будем избегать этого любой ценой, но если сочтём необходимым — можем изменить его
в рамках **минорного** апгрейда версии.

:::tip[Не хватает возможности? Заведите issue, а не тинкерите]
Правило простое: если вам чего-то не хватает или нужна какая-то возможность — **не тюнтье стартер**, а заведите
issue в нашем [трекере на GitHub](https://github.com/axelixlabs/axelix/issues). Мы обещаем, что рассмотрим. Когда мы
добавим запрошенную вами возможность, мы дадим вам **свойство** для управления этим поведением — стабильную,
поддерживаемую настрокйу, а не переопределение бина или зависимость на уровне кода.
:::
